# S4: Crew feasibility

**Verdict: GO (2026-11-24).** A Crew app in its own repository installs from a local path, is enabled after an operator trust grant, and its reviewer agent produced a fixed-format `review.md` through Crew from a sample proposal (entry 3). Crew remains outside the runtime. Its reviews are advice, not gates.

## Entry 1: 2026-11-24, first install (status: superseded by entry 2)

Tested:
- Kiro Crew is installed. The `kirocrew` command is not on `PATH`. It runs through the bundled Python: `<install>\resources\backend-dist\kirocrew-backend\python.exe -m kiro_crew ...`.
- `kirocrew app init` scaffolded an app. I replaced the samples with the agent `rule-change-reviewer` and the skill `rule-change-review`.
- `kirocrew app install <local path>` succeeded ("installed changeling-crew v0.1.0").
- The app lives in its own repository, `C:\Users\Administrator\Documents\kiro-work\changeling-crew`. No GitHub remote exists (GitHub CLI not installed).
- `kirocrew app enable` was refused until the operator trusts the app (setting `agent.apps_trusted`). I did not change this security setting.

Findings that still hold:
- Installing needs no network and no build step for an agent-plus-skill app.
- Enabling needs a human trust grant. Crew gates third-party code behind the operator.
- Crew docs say an app normally lives in its own repository, which matches the plan.

## Entry 2: 2026-11-24, reviewer could not find its skill or read and write files

**What happened.** After the developer enabled the app, the reviewer could not find its skill and could not read or write files. This was my configuration error, not a Crew defect.

**Cause (verified by reading the materialized agent `~/.kiro/agents/changeling-crew--rule-change-reviewer.json` and the Crew docs):**
1. `tools` was `["@kirocrew-core"]`. That reference mounts only Crew's core MCP server (spawn, learn, task, wait, messaging). It contains no file tools. I copied it from the docs' sample agent without checking what it grants.
2. The agent had no `resources` entry for the skill. Crew only symlinks the skill folder into `~/.kiro/crew/skills/`. Nothing told the agent to load it.
3. `SKILL.md` had no `name` in its frontmatter. The docs require `name` and `description`.

**Fix (in the `changeling-crew` repo):**
- `tools: ["fs_read", "fs_write"]`, `allowedTools: ["fs_read"]`, `toolsSettings.fs_write.allowedPaths: ["**/review.md"]`, `includeMcpJson: false`. No shell, no web, no MCP.
- `resources: ["skill://~/.kiro/crew/skills/rule-change-review/SKILL.md"]`.
- `SKILL.md` frontmatter now has `name`, `description`, and `triggers`.
- The installed `kiro-cli` is 2.27.1 (default engine v2), so the legacy fields `tools`, `allowedTools`, and `toolsSettings` apply. The V3 `permissions` field does not.

**Verified (2026-11-24, `kiro-cli chat --agent ... --no-interactive` in a temp workspace holding a copy of the agent and the sample proposal):**
- The skill was visible to the agent. The agent read `proposal.md` and `gate-report.json` and wrote `review.md` with the fixed headings and `DO NOT APPROVE`, because the required `ground-truth` gate is `missing`. The review also flagged real issues: an inconsistent `knownFrom` convention, and the married-filing-separately status, which the quoted text covers but the proposal ignores.
- Write guard: with a neutral prompt, creating `review.md` succeeded. Editing `proposal.md` was refused ("tool permission approval is not supported in non-interactive mode"), and the file hash was unchanged.
- `~` in a `skill://` path is expanded by `kiro-cli` (separate test, skill listed).

**Not verified:**
- The fixed app through Crew. The app now installed on this machine is the fixed version, but it is not enabled. The materialized agent file and the skill link under `~/.kiro/crew/skills/` do not exist.
- That Crew creates the `~/.kiro/crew/skills/rule-change-review` link on enable, which the `resources` path depends on. The path itself was tested with a different location.
- Behavior in an interactive Crew session, where a write outside `review.md` would prompt the user instead of being denied.

**Side effects and gotchas:**
- `kirocrew app install` refuses an existing app ("Uninstall first or use the update endpoint"). The update endpoint needs dashboard authentication, so I used uninstall then install. Uninstall revoked the per-app trust grant, so enable was refused again. Expect to re-trust after each reinstall, or use the dashboard's update action to keep the grant.
- Writing an agent JSON with PowerShell `Set-Content -Encoding UTF8` adds a BOM, and `kiro-cli` then reports "Mode ... not found". Write files without a BOM.

**Findings that change the design:**
- `allowedPaths` auto-approves writes to `review.md` and leaves other writes to approval. It is not a hard deny. The earlier statement that restriction is prompt-only is therefore incomplete: there is a tool-level guard, but it relies on approval. The integrity story still must not depend on the reviewer. Gates and signed approval carry that weight.
- The reviewer could not check the quote, tax year, or dates because the proposal directory had no snapshot. The proposal format must reference repo-relative snapshot paths, and the reviewer needs read access to them.

**Status:** fix applied and verified outside Crew (entry 2). Verified through Crew in entry 3.

## Entry 3: 2026-11-24, retest through Crew (status: closed, GO)

The developer re-trusted and enabled `changeling-crew`, then asked the reviewer to review `examples/sample-proposal/`. Result committed in the Crew repo at `986a359` (`examples/sample-proposal/review.md`). I checked it as follows.

**Verified by me:**
- Crew state: `installed.json` shows `enabled: true`. The materialized agent `~/.kiro/agents/changeling-crew--rule-change-reviewer.json` has `tools: [fs_read, fs_write]`, the `fs_write` `allowedPaths` entry for `**/review.md`, and the skill `resources` entry. The skill link `~/.kiro/crew/skills/rule-change-review` exists (symbolic link). The skill is therefore found through Crew, as the entry 2 fix intended.
- Output format: `review.md` has the six fixed headings in order.
- Recommendation: `DO NOT APPROVE` is correct. `gate-report.json` has the required gate `ground-truth` with status `missing`.
- Write scope: `proposal.md` and `gate-report.json` are unchanged against git. The only new file is `review.md`.
- The reviewer was honest about its limit. It said it did not open a snapshot, because the proposal names a `sourceId` and a hash but no file path. That matches the proposal.
- Source verification concern: valid. The proposal cites `us-irb-2025-45`, but that bulletin is dated 2025-11-03 (snapshot line 245). The proposal sets `knownFrom` to 2025-07-04. The same snapshot says Public Law 119-21 was signed into law on July 4, 2025. So 2025-07-04 is the enactment date, and the citation is a later document. The reviewer guessed this and could not confirm it.
- The quoted sentence exists in the snapshot (grep of `us-irb-2025-45/extracted.txt`, line 612). The reviewer could not check this, so I did.

**Not verified:**
- Whether Crew prompted for each read. The materialized `allowedTools` is `[]`, so Crew's governance removed the auto-approve for `fs_read`. I did not watch the session.

**Decision from the review (carried to task 5.5):** a rule version records why its `knownFrom` is what it is, using `knownFromBasis`: `enactment`, `publication`, or `snapshot-upper-bound`. When the basis is `enactment`, the version cites a quote stating the enactment date. This resolves the reviewer's concern and the JP upper-bound limitation from S2 with one field.

**Remaining limits:**
- Crew is advice only. Gates and signed approval decide.
- The proposal format must point to snapshot files so the reviewer can check quotes.
- Reinstalling revokes the trust grant. Use the dashboard's Update action.
