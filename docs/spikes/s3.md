# S3: Approval integrity (browser verification part)

## 2026-11-24: WebCrypto Ed25519 verification in a real browser (task 6.5)

- Question: can a browser verify signatures made with `node:crypto` over our canonical JSON?
- Command: `npm run typecheck` (builds `packages/core/dist`), then `node spikes/s3/browser-verify.mjs`.
  The script signs a payload with `generateApproverKey` and `signPayload`, serves a page from `http://127.0.0.1:<port>/` (a secure context), imports the built `webverify.js`, and reads the result with `--headless=new --dump-dom --virtual-time-budget=5000`.
- Browsers: Edge 158 and Chrome 158 (both headless, Windows).
- Outcome (verified): in both browsers a valid signature verified (`{ok:true}`), and the same signature over a payload with one changed field returned `BAD_SIGNATURE`. The payload included non-ASCII text, so canonical bytes matched across Node and browser.
- Code: `packages/core/src/webverify.ts` (`verifyPayloadWeb`, WebCrypto only, never throws). Node test: `packages/core/src/node/webverify.test.ts` (valid, tampered, bad key, non-integer payload).
- Not verified: Firefox and Safari. Non-headless mode. Browsers older than 158 (Ed25519 in WebCrypto is newer in some engines). Real approval records (no key exists yet, task 6.6). The page was served over loopback HTTP; a non-secure origin has no `crypto.subtle`, and `verifyPayloadWeb` returns `NO_WEBCRYPTO` there.
- Failed first attempt: the script used `execFileSync`, which blocked the event loop so the local server could not answer, and both browsers timed out. Fixed by using async `execFile`.
- Limit: the browser check detects modification of the pack, gate report, or lock only if the page also recomputes their digests. This spike checks the signature over a payload, not digest recomputation in the browser (SHA-256 via `crypto.subtle.digest` is not tested here).
- Verdict: **GO**. Browser-side verification is feasible, so the build-time fallback is not needed. No decision entry added.
- Next: task 6.6 is a human step. Run `keygen` and keep the passphrase private.

## 2026-11-25: Private key protection on Windows and key trust (task 6.7)
- Context: `keygen` wrote the key with `mode: 0o600`, which has no effect on NTFS. The repo public key was also trusted without an anchor. Dummy keys and temp files only. No real key was generated.
- KDF and cipher (verified). Command: a throwaway script `spikes/s3/out/kdf.mjs` (not committed, `out/` is ignored) generated an Ed25519 key with `privateKeyEncoding {type:"pkcs8", cipher:"aes-256-cbc", passphrase}` and walked the DER. Node 26.13.1, OpenSSL 3.5.9. Result: PEM `ENCRYPTED PRIVATE KEY`, PBES2 (1.2.840.113549.1.5.13), PBKDF2 (…5.12) with a 16-byte salt, **2048 iterations** (INT 0x0800), PRF HMAC-SHA256, cipher AES-256-CBC (2.16.840.1.101.3.4.1.42) with a 16-byte IV. Node exposes no option for the iteration count on export.
- Assessment: AES-256 is fine. 2048 PBKDF2 iterations is low by current guidance (OWASP lists 600,000 for PBKDF2-HMAC-SHA256), so a stolen file allows a fast offline guess. The passphrase is therefore the protection. Change made: `keygen` requires at least 16 characters (was 8). Not done: a scrypt wrapper around the DER (would need our own file format). Status: open, optional. Not measured: guess rate on real hardware.
- ACL before (verified), on a dummy file in `%TEMP%`: `icacls` showed inherited entries `(I)` for `CodexSandboxUsers` (M), an unnamed SID (M), an app-container SID (F), `Administrator` (F), `NT AUTHORITY\SYSTEM` (F), and `BUILTIN\Administrators` (F). So the default file was readable by others, including SYSTEM and all Administrators.
- ACL fix (verified): `icacls <file> /inheritance:r` then `icacls <file> /grant:r *<SID>:F`, with the SID from `whoami /user /fo csv /nh`. Result: a single ACE `EC2AMAZ-EG4LE9D\Administrator:(F)`, and the file stayed readable by the same user.
- Code: `packages/core/src/node/acl.ts` (`restrictToCurrentUser`), called by `keygen` after writing the key. On failure `keygen` deletes the key file, prints the cause, and exits 1. Tests: `acl.test.ts` (real icacls on a temp file, skipped when not win32; injected-failure and non-win32 cases always run) and a CLI test for the failure path.
- Not verified: ACL behaviour on non-NTFS volumes or domain-joined accounts; that administrators cannot take ownership (they can, by design of Windows); a brief window between file creation and the ACL change, where the file has inherited permissions (the content is encrypted). Non-win32 still relies on mode 0600 only.
- Trust anchor tests (verified, `npm test`, 114 tests pass): key substitution with a valid re-sign is rejected (`untrusted-key`), a missing or malformed anchor fails closed (`no-trust-anchor`), the correct anchor passes. Documented limit: swapping key and anchor together passes (test "anchor and key changed together").
- Status: done, except task 6.6 (human keygen), which runs after this.

The ID match shows consistency between two repo files, not that the key belongs to the intended person.

## 2026-11-26: Task 7.2 PreToolUse guard hook
- What: added `.kiro/hooks/guard-protected-paths.json` (PreToolUse, matcher `fs_write|fs_append|str_replace|delete_file|execute_pwsh|execute_bash|smart_relocate`) and `.kiro/hooks/guard-protected-paths.mjs`. The script reads the hook JSON on stdin and returns `permissionDecision: "ask"` when the tool input names a `ground-truth` or `approvals` path segment. `ground-truth-candidates` is not matched.
- Verified: ran the script by hand with sample payloads. `ground-truth/` and `approvals/` paths return "ask". A `ground-truth-candidates/` path returns nothing.
- Not verified: that Kiro fires the hook in a live session (it activates at the next session start), and the exact stdin field names Kiro sends (the script falls back to scanning the whole payload).
- Limits: the hook is a guard rail. Shell commands that build the path indirectly (variables, globs) are not caught. The digest lock and signature check remain the enforcement.
- Status: done, pending live confirmation.

## 2026-11-26: Task 7.2.1 Ground-truth schema fix
- What: `GroundTruthExampleSchema` (packages/core/src/groundtruth.ts) allowed only scalar facts and accepted an empty `expected`. JP facts use `children: [{ birthDate }]`, so JP examples could never pass `attest`. An empty `expected` would have asserted nothing.
- Fix: `facts` and `expected` now take a recursive JSON value (safe integer, string, boolean, null, array, object). Floats are rejected at any depth. `expected` must have at least one key.
- Verified: new `packages/core/src/groundtruth.test.ts` (in-memory; US flat facts, JP nested facts, nested float rejection, empty `expected`, NaN/undefined, unknown keys, bad date). `npm run typecheck` clean; `npm test` 15 files, 133 tests pass.
- Not verified: no real ground truth exists yet, and `attest` was not run on real apps. The `ground-truth-candidates` files are not validated against this schema.
- Status: done.
